# IC Group — кабинеты клиента и администратора

Клиентский сервис по [ТЗ](TZ.md): публичная форма `/`, регистрация перед отправкой, свои заявки `/requests` и демонстрационный обзор `/demo/cabinet`. React + TypeScript + Vite, FastAPI, PostgreSQL и Alembic. Интерфейс на русском языке, для компьютера и телефона; дизайн ориентирован на [основной сайт IC Group](https://www.ic-group.kz/).

## Кабинет IC Group

Откройте `/admin` (локально: http://localhost:5173/admin, Docker: http://localhost:8080/admin). Вход общий с клиентской частью; доступ к рабочим заявкам требует роли `manager`. Заявка из публичной формы появляется в кабинете сотрудника, изменение статуса сохраняется в PostgreSQL и видно клиенту в `/requests`.

В Windows из корня проекта: `powershell -ExecutionPolicy Bypass -File scripts/start-admin.ps1`. Скрипт использует установленный Node.js либо локальную версию в `.tools`. На другом компьютере сначала установите Node.js 22.12+ и выполните `npm ci` в `frontend`. Обычный запуск через `npm run dev` также работает. Для рабочих заявок нужен запущенный backend; `/demo/admin` доступен без него.

- `/admin/requests` — реальные анкеты клиентов: контакты, несколько объектов, индивидуальные графики, услуги, бюджет и желаемое начало. Поиск, фильтры, CSV, загрузка следующих 50 записей, история и статусы «новая / в работе / связь установлена / закрыта». Цена не выдумывается: до расчёта показано, что смета не подготовлена.
- `/demo/admin/requests` — сохранённый демонстрационный набор анкет и предварительных цен.
- `/demo/admin/projects` — демонстрационные проекты, отчёты по участкам, рабочее время, отдельные условия и сметы субподрядчиков, материалы, версии и состояния документов/выплат. Фото и договоры без файлов показываются как отсутствующие.
- `/demo/admin/complaints` — демонстрационные возражения клиента, рассмотрение в IC Group, отдельное подтверждение передачи исполнителям, ответ и история. Передача и ответ не отправляют уведомления.

Рабочие анкеты доступны только сотрудникам и не сохраняются в localStorage. Поиск и CSV работают по загруженным записям; для следующей страницы есть «Загрузить ещё заявки», для обновления списка — «Обновить заявки». Обычная регистрация всегда создаёт клиента; роль сотрудника выдаётся административной командой ниже. Демо хранит только вымышленные записи и локальные изменения. Рабочие проекты и претензии ещё не подключены: ссылки явно открывают демонстрацию, старые `/admin/projects` и `/admin/complaints` перенаправляют сотрудника туда.

Структура и состав чек-листа импортированы из `02_Чек-листы_стандарт_и_пример.xlsx`, лист «Пример — Вента, ТРЦ Норд», строки 5–14. Базовые работы составляют 190 человеко-минут, доступно по примеру 360; генеральная уборка (960 человеко-минут) учитывается отдельно. Для тестовых проектов используется один пример. Повторный импорт: `python scripts/import_admin_checklist.py`.

`frontend/src/features/admin/service.ts` содержит отдельные адаптеры рабочих заявок FastAPI и демонстрационных данных. `/admin` проверяет профиль на клиенте, а API независимо проверяет роль на сервере. Модуль загружается отдельно; публичная форма остаётся на `/`, демонстрационный клиентский обзор — на `/demo/cabinet`.

Фирменные цвета, Montserrat и логотип взяты с [основного сайта IC Group](https://www.ic-group.kz/). Логотип хранится локально в `frontend/public/brand/ic-group.png`; шрифт поставляется через npm. Административные стили ограничены `.ic-admin`.

Проверки кабинета без backend, из `frontend`: `npm run build`, `npx playwright install chromium`, `npm run test:ui -- tests/admin.spec.ts`.

Проверено: production-сборка, 9 браузерных сценариев, ширины 1440/390/320 px, сохранение статусов, доступ исполнителей только после явной передачи в демо, экспорт и восстановление после ошибки локального хранилища. Повторный импорт чек-листа даёт тот же снимок. Скриншоты можно повторить командой `node scripts/capture-admin.mjs` из `frontend` при запущенном Vite.

## Реализовано

- Форма без входа: до 20 объектов, тип, сегмент, название, город, адрес, площадь, индивидуальные графики основной и поддерживающей уборки, санузлы, материалы, генеральная уборка, пожелания, необязательные начало и бюджет.
- Черновик сохраняется локально в браузере; контакты и пароль в черновик не записываются. При недоступном хранилище интерфейс предупреждает, что нельзя закрывать вкладку.
- Регистрация по email и паролю, имя, телефон и компания; вход и выход. После регистрации форма остаётся заполненной, отправка подтверждается отдельным действием.
- Отправка требует серверной сессии. Заявка сохраняет снимок параметров и контакты из профиля; повторная отправка с тем же ключом возвращает ту же заявку.
- Свои заявки и их подробности доступны только автору. Для сотрудников — защищённый API списка и изменения состояния, с историей.
- Настоящий логотип IC Group, локальный Montserrat, белый/графитовый/зелёный интерфейс, клавиатурная навигация и мобильная версия.
- Обзор ТОО «Медеу Девелопмент» и объекта ТРЦ «Норд».
- Архив за сентябрь 2026: выбор дня, переход по неделям, группировка работ и раскрытие списка.
- 729 плановых смен и 705 смен с обеими отметками времени. Отметки не означают приёмку уборки.
- Загрузка, ошибки с повторной попыткой, пояснения об отсутствующих документах.
- PostgreSQL, миграции, повторяемый демо-импорт, API и конфигурация развёртывания.

Форма сейчас отправляет **заявку на расчёт менеджером**. Автоматическая смета с ценой, НДС и версией нормативов — отдельный следующий этап; произвольные тарифы не используются. Подтверждение email, восстановление пароля, рабочие проекты и претензии, отдельные страницы объектов/договоров, загрузка файлов и АВР ещё не реализованы.

Демонстрационный обзор отделён от нового аккаунта. Публичный API `/api/v1/demo/overview` работает только при `DEMO_MODE=true` и ограничен очищенным набором одного демо-клиента. Регистрация с совпадающим названием компании не даёт доступ к существующей организации: создаётся отдельная запись, последующее объединение требует проверки менеджером.

## Аккаунты и обработка заявок

Пароли хешируются Argon2id, в PostgreSQL хранится хеш случайного токена сессии. Сессия живёт 12 часов и отзывается при выходе. В браузере токен хранится в `sessionStorage` для текущей вкладки; API использует Bearer-заголовок, поэтому отдельные домены Vercel/Render не зависят от сторонних cookie. Запросы входа/регистрации ограничиваются по email и адресу соединения. Схема авторизации следует [рекомендации FastAPI по pwdlib/Argon2](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/), с серверными отзываемыми сессиями вместо JWT.

В регистрации нет подтверждения владения email. SMTP/SMS и внешние уведомления не подключены; менеджер работает с сохранёнными заявками через `/admin/requests` и защищённый API. Для развёртывания используйте HTTPS и точный `FRONTEND_ORIGIN`.

Чтобы выдать доступ сотруднику, сначала зарегистрируйте его аккаунт, затем из `backend` выполните административную команду:

```sh
python -m app.create_manager manager@example.com
```

Для Docker: `docker compose exec backend python -m app.create_manager manager@example.com`. Публичная регистрация не принимает роль. После получения токена через `/api/v1/auth/login` сотрудник может использовать Swagger `/docs` → **Authorize**:

- `GET /api/v1/staff/requests?offset=0` — заявки и контакты, по 50 на страницу.
- `PATCH /api/v1/staff/requests/{id}` — `{"status":"in_review"}`; состояния: `new`, `in_review`, `contacted`, `closed`.
- `GET /api/v1/requests` и `GET /api/v1/requests/{id}` — только собственные заявки клиента.

## Docker

Нужен запущенный Docker Desktop или Docker Engine с Compose.

```sh
docker compose up --build -d
```

- Форма: http://localhost:8080/
- Заявки: http://localhost:8080/requests
- Демо кабинета: http://localhost:8080/demo/cabinet
- API: http://localhost:8000/docs
- Готовность базы/API: http://localhost:8000/health/ready
- PostgreSQL: localhost:5433, база `ic`, пользователь `ic`, локальный демо-пароль `ic_local_demo`.

Миграция и демо-импорт выполняются при старте backend. Данные сохраняются в Docker volume; `docker compose down` их сохраняет. Порт базы и локальный пароль можно изменить через корневой `.env` по образцу `.env.example`.

```sh
docker compose logs -f backend
docker compose down
```

## Разработка

Нужны Python 3.12+, Node.js 22.12+ и PostgreSQL. Базу можно запустить отдельно:

```sh
docker compose up -d db
python -m venv .venv
```

Активируйте `.venv`: `.venv\Scripts\Activate.ps1` в PowerShell или `source .venv/bin/activate` в bash. Затем:

```sh
pip install -r backend/requirements-dev.txt
cd backend
```

Создайте `backend/.env` по образцу `backend/.env.example`:

```sh
alembic upgrade head
python -m app.seed
uvicorn app.main:app --reload
```

Во втором терминале:

```sh
cd frontend
npm ci
npm run dev
```

Откройте http://localhost:5173/. Vite пересылает `/api` на backend:8000. Для другого адреса задайте `VITE_API_URL` перед запуском или сборкой.

Фотографий и оформленных в системе АВР в наборе нет. Наличие исходного PDF не означает публикацию или подписание договора в кабинете.

## Проверки

Из `backend` в активированной `.venv`:

```sh
python -m pytest -q
```

Проверяются контрольные суммы, выбор даты, изоляция демо, повторный импорт, Argon2, отзыв/истечение сессий, обязательность входа, ограничения полей, сохранение нескольких объектов, повторная отправка, изоляция клиентских заявок и права сотрудников. Тесты используют SQLite в памяти; рабочая база — PostgreSQL.

Из `frontend`:

```sh
npm run build
npx playwright install chromium
npm run test:ui
```

Для UI-тестов backend должен работать на localhost:8000 с демо-данными. Vite запускается автоматически. Для контейнерной версии задайте `TEST_BASE_URL=http://localhost:8080`. Проверяются смена даты, раскрытие списка, мобильная навигация и восстановление после ошибки.

Связка клиента и сотрудника проверяется в `frontend/tests/admin-live.spec.ts`. Для полного сценария задайте `TEST_DATABASE_URL` с адресом **тестовой базы работающего API**: тест регистрирует отдельные аккаунты с адресами `@example.com`, выдаёт одному роль сотрудника через CLI, отправляет форму и сверяет статус в обоих кабинетах. Без этой переменной только этот сценарий пропускается. При необходимости задайте `TEST_API_URL` (по умолчанию `http://127.0.0.1:8000`) и `TEST_PYTHON` (по умолчанию Python из корневой `.venv`). Остальные проверки доступа и пагинации запускаются без прямого доступа к базе.

Проверка объединённой версии: production-сборка, 11 тестов API и 23 браузерных сценария прошли (11 клиентских, 9 административных демонстрационных и 3 интеграционных). На работающих FastAPI/PostgreSQL проверен путь «форма клиента → заявка сотруднику → изменение статуса → тот же статус у клиента», включая отказ сохранения и повтор, ограничения роли и выход из аккаунта. Проверены пагинация и истечение сессии. После исправления переполнения шапки повторно пройдены проверки на 320/390 px; один конфликт файлов отчёта между параллельными запусками устранён отдельным повтором теста. Обе миграции и импорт ранее проверены на отдельной локальной PostgreSQL 18; схема при слиянии не изменялась. Синтаксис Compose проверен; сборка и запуск контейнеров остаются непроверенными из-за ранее обнаруженной ошибки API 500 установленного Docker Desktop. Render и Vercel пока не развёрнуты.

## Render

Корневой `render.yaml` создаёт PostgreSQL и Docker-сервис backend через Blueprint. Укажите `FRONTEND_ORIGIN` — origin сайта Vercel без пути и завершающего `/`. `DATABASE_URL` привязывается к базе автоматически, `PORT` передаёт Render. Миграции выполняются перед запуском API.

Для демонстрации первого экрана включён `DEMO_MODE=true`. После реализации входа его можно отключить. Публикация автоматически не выполняется. Формат конфигурации: [Render Blueprint](https://render.com/docs/blueprint-spec).

## Vercel

1. Импортируйте репозиторий, задайте **Root Directory: `frontend`**, framework Vite.
2. Команда сборки: `npm run build`, каталог результата: `dist`.
3. Задайте `VITE_API_URL=https://<имя-сервиса>.onrender.com` и пересоберите сайт.
4. Добавьте origin Vercel в `FRONTEND_ORIGIN` backend. Для нескольких окружений допустим список origin через запятую.

`frontend/vercel.json` обеспечивает открытие `/requests/{id}` и других маршрутов по прямой ссылке. Переменная `VITE_API_URL` содержит только публичный URL API. Документация: [Vite on Vercel](https://vercel.com/docs/frameworks/frontend/vite).

## Продолжение

Работа идёт по одному согласованному экрану:

1. Автоматическая смета с проверкой Z-01; подтверждение email, восстановление доступа, подключение рабочих проектов и претензий.
2. Карточка объекта: план, сроки услуг, чек-листы и фото до/после.
3. Договоры: публикация менеджером, версии, сроки и отдельный статус подписания.
4. Претензии в IC Group, история и управляемая передача исполнителям.
5. АВР, приёмка и отдельно подтверждённые оплаты.

Схема БД развивается миграциями Alembic. Демонстрационный импорт отделён от будущих рабочих данных. Функциональные модули UI — в `frontend/src/features`, общие компоненты — в `components`.
