# IC Group — клиентский сервис

Сервис управления клинингом по [ТЗ](TZ.md): заявки клиентов, объекты, смены, фотоконтроль, обращения по качеству, акты и расчёты.

**Стек:** React · TypeScript · Vite · Python FastAPI · PostgreSQL · SQLAlchemy · Alembic. PDF формируются через ReportLab; ИИ-поддержка использует Groq. Интерфейс на русском, время операций отображается в UTC+5.

Рабочие кабинеты используют API и PostgreSQL. Демо-аккаунты и примеры объектов автоматически не создаются. Учебная платформа выплат — отдельная интеграция из ТЗ: она не переводит реальные деньги.

## Кабинеты и роли

| Роль | Раздел | Возможности |
| --- | --- | --- |
| Клиент | `/cabinet`, `/requests` | Свои заявки и объекты, график, фотоотчёты, документы, приёмка АВР, обращения по качеству |
| Администратор | `/admin` | Все клиентские заявки, создание объектов из заявок, условия обслуживания, закрепление субподрядчиков, документы и расчёты, создание работников и субподрядчиков |
| Суперадминистратор | `/admin` | Возможности администратора, дополнительно создание и управление администраторами |
| Субподрядчик | `/contractor` | Закреплённые объекты, приглашения работников на смены, задания по зонам, проверка фотоотчётов, подтверждение клининга, начисления и учебные выплаты работникам |
| Работник | `/work` | Приглашения на смены, свои задания, фото до/после, чек-листы, приёмка собственных начислений, IC-coins |

Клиентские заявки отправляют только клиенты. Администраторы, субподрядчики и работники не могут отправлять их через свои аккаунты. Только субподрядчик планирует уборки и приглашает исполнителей.

Администраторы управляют аккаунтами работников и субподрядчиков; субподрядчики — только созданными ими работниками. Приглашение работника из общей базы не передаёт управление его аккаунтом. Отключение аккаунта завершает его сеансы; блокировка субподрядчика также ограничивает вход созданных им работников. Любой администратор может заблокировать объект: новые работы приостанавливаются, история сохраняется.

## Основной сценарий

1. Посетитель заполняет многообъектную форму на `/`. Для отправки регистрируется: email, пароль, имя, телефон и компания. Повтор отправки не создаёт копию заявки.
2. Администратор обрабатывает заявку и создаёт связанные объекты, заполняет условия и закрепляет субподрядчика. Повторное создание возвращает уже существующие объекты.
3. Субподрядчик задаёт зоны, даты, время, обязанности и выбирает свободных работников из общей базы.
4. Работник принимает или отклоняет приглашение в `/work/invitations`. До согласия время не резервируется; при принятии повторно проверяются пересечения и нормы отдыха.
5. Работник загружает фото «до», начинает работу, выполняет чек-лист, загружает фото «после» и отправляет отчёт.
6. После выполнения всех активных зон субподрядчик подтверждает клининг целиком. Клиент видит результат, время и фотоотчёты без дополнительной приёмки администратором.
7. По подтверждённым работам формируются акты и начисления за выбранный период.

Проверки расписания учитывают пересечения, переезды и отдых по нормативам пакета. Уведомления о приглашениях обновляются в кабинете; email и SMS не отправляются.

### Обращения и файлы

Обращение по качеству изначально видят клиент и IC Group. Администратор может перенаправить его исполнителю, отозвать доступ и окончательно закрыть обращение. Клиент видит решение и может продолжить переписку.

Файлы хранятся в PostgreSQL; скачивание требует авторизации и доступа к объекту. Фото принимаются в JPEG/PNG/WebP до 8 МБ и 20 Мп, уменьшаются до 2048 пикселей по длинной стороне и сохраняются без EXIF. Исходники отдельно не хранятся. Время получения фото не считается доказательством времени съёмки. Загружаемые договоры, приложения и АВР принимаются в PDF до 8 МБ; предыдущие файлы сохраняются.

## Акты и расчёты

В карточке объекта открыт раздел **«Акты и расчёты»**.

| Документ | Кто формирует | Кто принимает |
| --- | --- | --- |
| АВР клиенту | Администратор / суперадминистратор | Клиент объекта |
| Акт субподрядчика | Администратор / суперадминистратор | Указанный субподрядчик |
| Начисление работнику | Субподрядчик | Указанный работник |

Для формирования нужны номер договора в условиях объекта и принятые работы за период. Ответственный выбирает работы, подтверждает объёмы, единицы, тарифы **без НДС**, ставку НДС, условия оплаты и основание согласованной сметы. Для корректировки обязательно основание. Сервер рассчитывает суммы и НДС, сохраняет состав документа и формирует PDF с кириллицей.

Цикл документа: **черновик → на приёмке → принят / отклонён**. Отклонённый документ можно отменить с причиной и сформировать исправленный. Отменённый остаётся в истории; его работы освобождаются для нового акта. Принятый акт отменить через этот сценарий нельзя.

Одна работа не может входить в два действующих акта одного вида, даже при пересекающихся периодах. Клиент не видит расчёты субподрядчика и работников; работник видит только собственные начисления.

После приёмки возникает состояние **«Начислено»**, затем отдельно **«К оплате» → «Выплата отправлена» → «Оплачено»**. Генерация PDF и приёмка не означают оплату. Подтверждение через аккаунт фиксирует автора и время, но **не является ЭЦП**.

### Учебная платформа выплат

Выплаты работникам интегрированы с [учебной Платформой Занятости](https://hack.ic-group.kz/platform). Реальные деньги не переводятся; используются вымышленные ИИН из пакета кейса.

- Backend требует `PLATFORM_API_KEY`. Ключ команды 28 получен с разрешения команды и сохранён в локальном, игнорируемом `backend/.env`; в Git он не публикуется.
- Субподрядчик переводит принятое начисление к оплате и вводит учебный ИИН получателя. Начисление должно относиться к одному календарному месяцу.
- Тело запроса и постоянный ключ операции сохраняются **до** обращения к платформе. При таймауте отправку повторяют с тем же ИИН — повтор использует тот же ключ.
- Платформа возвращает `processing`, затем `paid` или `failed`. Кнопка **«Проверить статус выплаты»** получает подтверждённый результат через API; автоматический опрос событий не подключён.
- После подтверждённого отказа доступна новая попытка. Поздний ответ прежней попытки не должен изменять новую.
- Комиссия плательщика начисляется сверх суммы работнику: `сумма × 6% / 94%`. В интерфейсе показываются комиссия и полное списание из ответа платформы.

Платежи клиента и субподрядчика фиксируются вручную по внешнему платёжному подтверждению. Банковская отправка из кабинета для них не реализована.

## ИИ-поддержка

Раздел доступен по `/cabinet/support`, `/admin/support`, `/contractor/support`, `/work/support`. Роль берётся из серверной сессии; инструкции по возможностям находятся в `backend/app/support_knowledge.py` и должны обновляться вместе с продуктом.

Настройки: `GROQ_API_KEY` и `GROQ_MODEL` (по умолчанию `openai/gpt-oss-120b`). Ключ хранится только на backend. История каждого аккаунта сохраняется отдельно в PostgreSQL. В Groq передаются инструкции, имя и роль, новый вопрос и ограниченная часть собственной истории текущей роли.

Помощник объясняет интерфейс, но не изменяет данные и не читает текущие статусы объектов. Ответы ИИ могут содержать ошибки. Вопрос ограничен 4000 символами, одновременно обрабатывается один ответ на аккаунт, действует лимит 30 попыток в час. При сбое доступен повтор; перезагрузка не удаляет историю.

## IC-coins

`/work/ic-coins` — баланс, запросы бонусов и история. `/contractor/ic-coins` — рассмотрение бонусов собственных работников.

Новому работнику один раз начисляются 1000 стартовых монет. Существующим аккаунтам они задним числом не выдаются. Бонус подтверждает только создавший работника субподрядчик; для работников без такого владельца запрос бонуса недоступен. Повтор подтверждения не начисляет монеты повторно.

Каталог и баланс хранятся на сервере, покупка защищена от повторного списания. Курс магазина: 1 IC-coin = 2 ₸. Заказ ожидает выдачи; автоматическая выдача товаров и купонов не подключена.

## Быстрый запуск через Docker

1. Скопируйте `.env.example` в `.env`.
2. Заполните `POSTGRES_PASSWORD`, `SUPERADMIN_EMAIL`, `SUPERADMIN_PASSWORD`. Пароль суперадминистратора: 12–128 символов.
3. Для ИИ и учебных выплат добавьте соответствующие API-ключи в корневой `.env`.
4. Запустите:

```sh
docker compose up --build
```

| Сервис | Адрес |
| --- | --- |
| Сайт | http://localhost:8080 |
| Администратор | http://localhost:8080/admin |
| OpenAPI | http://localhost:8000/docs |
| Готовность базы | http://localhost:8000/health/ready |

Миграции и создание суперадминистратора выполняются при старте. Записи и файлы сохраняются в PostgreSQL volume; `docker compose down` его не удаляет. Для пароля базы в строке подключения нужны URL-безопасные символы либо URL-кодирование. Локальный Uvicorn и Docker используют один порт 8000 — не запускайте их одновременно.

## Переменные окружения

| Переменная | Где нужна | Назначение |
| --- | --- | --- |
| `DATABASE_URL` | Backend / Render | Подключение PostgreSQL; Render URL `postgresql://…` поддерживается |
| `FRONTEND_ORIGIN` | Backend / Render | Разрешённые адреса frontend через запятую, без пути и завершающего `/` |
| `SUPERADMIN_EMAIL` | Backend / Compose / Render | Email суперадминистратора |
| `SUPERADMIN_PASSWORD` | Backend / Compose / Render | Пароль суперадминистратора |
| `GROQ_API_KEY` | Backend / Compose / Render | Секрет Groq для ИИ-поддержки |
| `GROQ_MODEL` | Backend / Compose / Render | По умолчанию `openai/gpt-oss-120b` |
| `PLATFORM_API_KEY` | Backend / Compose / Render | Секрет учебной платформы выплат |
| `POSTGRES_PASSWORD` | Корневой `.env` для Compose | Пароль локальной базы Docker |
| `POSTGRES_PORT` | Корневой `.env` для Compose | Внешний порт локальной базы, по умолчанию `5433`; внутри Docker — `5432` |
| `VITE_API_URL` | Frontend / Vercel | Адрес backend без `/api/v1`, например `https://ic-group-api.onrender.com` |

Пустые значения в `.env.example` — места для ваших секретов. Настройки локального Docker и управляемой базы Render различаются: `POSTGRES_PORT=5433` не нужно переносить на Render.

При локальном запуске backend сначала читает корневой `.env`, затем `backend/.env`; переменные процесса имеют приоритет. **Локальные файлы `.env` автоматически на Render не переносятся.** Compose получает значения из корневого `.env`, а не из `backend/.env`.

Не помещайте секреты в `VITE_*`, примеры окружения или Git. Ранее опубликованный ключ нужно отозвать и заменить: удаления из текущего файла недостаточно для удаления из истории.

### Суперадминистратор

После миграций `python -m app.bootstrap` создаёт аккаунт из окружения. Повторный запуск не создаёт копию. Изменение пароля обновляет его хеш и завершает сеансы. Существующий обычный аккаунт не повышается автоматически до суперадминистратора.

Изменение email может создать отдельного суперадминистратора; не используйте это как переименование аккаунта. Пароли созданных сотрудников передаются лично: автоматическая отправка email не подключена.

## Развёртывание: Render + Vercel

### Backend на Render

`render.yaml` описывает PostgreSQL и Docker backend с корнем `backend`. При ручной настройке укажите те же параметры.

В **Environment** задайте `DATABASE_URL`, `FRONTEND_ORIGIN`, `SUPERADMIN_EMAIL`, `SUPERADMIN_PASSWORD`, `GROQ_API_KEY`, `GROQ_MODEL`, `PLATFORM_API_KEY`. В Blueprint `DATABASE_URL` связывается с созданной базой; секреты заполняются отдельно.

Пример разрешённого origin: `https://28-command-82-83-84.vercel.app`. После изменения окружения сохраните настройки с перезапуском сервиса. Health check: `/health/ready`.

`backend/start.sh` выполняет:

```sh
alembic upgrade head
python -m app.bootstrap
uvicorn app.main:app --host 0.0.0.0 --port "${PORT:-8000}"
```

### Frontend на Vercel

- Root Directory: `frontend`.
- Install Command: `npm ci`.
- Build Command: `npm run build`.
- Output Directory: `dist`.
- Environment: `VITE_API_URL=https://ic-group-api.onrender.com`.

После изменения `VITE_API_URL` нужна новая сборка frontend. Добавьте фактический домен Vercel в `FRONTEND_ORIGIN` backend. API-ключи на Vercel не требуются. Для изменений актов и выплат обновляйте **оба** сервиса.

## Локальная разработка

Python 3.12+, Node.js 22.12+, PostgreSQL 16+.

```sh
python -m venv .venv
# Windows: .venv\Scripts\activate
# Linux/macOS: source .venv/bin/activate
pip install -r backend/requirements.txt
cd backend
# Создать .env по .env.example и заполнить DATABASE_URL и данные суперадминистратора
alembic upgrade head
python -m app.bootstrap
uvicorn app.main:app --reload --port 8000
```

В другом терминале:

```sh
cd frontend
npm ci
npm run dev
```

Vite проксирует `/api` на `http://127.0.0.1:8000`. Сайт: http://localhost:5173.

## Миграции и проверки

Текущая цепочка миграций заканчивается ревизией `c28a14f03006`: акты и расчёты. `c28a14f03005` — ИИ-поддержка, `c28a14f03004` — IC-coins, `c28a14f03003` — блокировки. Прежняя коллизия номера `03` устранена; не возвращайте старый файл миграции монет с этим номером. Docker build проверяет уникальность ревизий и наличие одной вершины графа.

Команды для отдельного запуска проверок:

```sh
# Из backend; pytest устанавливается отдельно
python -m pip install pytest
python -m pytest tests -q
python -m alembic heads

# Из frontend
npm run build
npm run test:ui
```

Живые тесты Groq включаются через `TEST_SUPPORT_LIVE=1`. Тест IC-coins — через `TEST_COINS=1`, `TEST_COINS_ROOT_EMAIL`, `TEST_COINS_ROOT_PASSWORD`; адрес API переопределяется `TEST_API_URL`. Такие сценарии создают аккаунты и операции: используйте отдельную тестовую базу. Groq-запросы расходуют лимиты сервиса.

**Состояние проверки:** базовые сценарии актов, PDF и первоначальная миграция проверялись. После добавления учебных выплат и последних правок интерфейса финальные проверки не выполнялись. Наличие реализации не означает, что новая интеграция уже проверена на Render.

## Известные ограничения

- Нет ЭЦП и автоматического извлечения тарифов из договоров: основание, объёмы и цены подтверждает ответственный.
- Нет массового бухгалтерского закрытия всех договоров за месяц и банковских переводов клиенту/субподрядчику.
- Выплаты работникам используют только учебную платформу; статус проверяется по запросу пользователя.
- Приёмка аккаунтом, загрузка подписанного документа, начисление и подтверждённая оплата — разные факты.
- Нет автоматической отправки email/SMS и выдачи товаров за IC-coins.
- ИИ-помощник не выполняет операции и не гарантирует безошибочность ответов.

## Частые проблемы

- **503 при отправке в ИИ-поддержку:** проверьте `GROQ_API_KEY` именно в окружении backend Render и перезапустите сервис. Чтение истории не требует ключа Groq.
- **CORS:** проверьте точное совпадение origin frontend с `FRONTEND_ORIGIN` и доступность API. Настройки Vercel не заменяют настройки backend.
- **Multiple head revisions:** убедитесь, что Render собирает актуальную ветку и в ней нет старого дубликата миграции. Не обходите конфликт заменой `head` на `heads`.
- **Не формируется акт:** заполните номер договора, выберите период завершения работ в UTC+5 и убедитесь, что уборки приняты и ещё не включены в действующий акт того же вида.
- **Неизвестен результат выплаты:** повторите отправку с тем же ИИН либо проверьте статус существующей выплаты. Не создавайте другое начисление ради повтора.
